# Native SDK — open findings

Register of open findings from three audits of `sdk/android`/`sdk/ios` (round 1 over the first tree, round 2 at `51d923ded`, round 3 at `2ae125a71`). Only what is still open or partial is listed; closed findings are one line each in §4. Ids are kept from the original documents (`B*/S*/C*/N*/A*/D*/T*` from round 1, `2.x/3.x/4.x/5.x/8.x` from round 2, `9.x` new in round 3) so commit messages and review notes still resolve.

Rounds 1 and 2 were static. Round 3 ran both suites: iOS 366 tests / 37 suites green, Android 132 tests green (15.4s, >65% of it one test — see T6). That Android number is the round-3 count and has not been re-run since; `sdk/android/README.md`'s own `@Test` grep reports ~420 today, most of the growth in `frak-sdk-ui`. Evidence line numbers were re-resolved against the tree at round 3. The five commits of `09-android-api-surface.md` have since moved many of them, so anchors in files that branch touched name the member rather than a line. Two iOS-only passes have since landed on top of round 3, Android untouched: the first closed or narrowed several 9.x rows and added two more (9.16, 9.17), the second moved identity storage off `UserDefaults` and closed 3.3, narrowing S4 and S3 with it. The iOS suite is now **394 tests in 42 suites** (`bun run --cwd sdk/ios test`), and evidence anchors in the files these passes touched were re-resolved against that tree.

ABI-irreversible or verification-blocking. Everything else can ship late. Two of the three rows below are now decided rather than blocking — they stay in this section, with their state in bold, because the *work* they decided is still landing and the record of why is worth keeping next to what it blocked. A fourth row, iOS's Swift 6 tools-version floor (B4/B5/1.5), closed outright this pass rather than merely being decided, and is retired to §4 instead of kept here — nothing about it is still landing.

### 3.7 The largest un-pinned surface

Not a bug — the highest-leverage structural gap. No golden corpus for URL query editing, gap-fill and attribution merge: **303 lines of code (478 raw), not the ~230 previously recorded**, hand-ported three ways (`queryParams.ts`/`UrlQuery.kt`/`URLQuery.swift`, `mergeAttribution.ts`/`AttributionParams.kt`/`SharingLinkBuilder.swift`), encoding a case-insensitive `fCtx` lookup, tolerant percent-decoding, "never re-encode the merchant's URL", empty-value skipping and a seven-field precedence rule. `golden-sharing-links.json` would close it the way `golden-context.json` closed the codec — note that fixture lives in `sdk/core/src/context/fixtures/`, referenced by path from both native suites, and covers only the binary `fCtx` codec.

Round 3 found three concrete instances of the drift this section predicts:

- **9.11 — the TS reference does not implement "never re-encode the merchant's URL."** `frakContext.ts`'s `update()` round-trips through `URLSearchParams`/`URL.toString()`, which re-serialises the entire query on any mutation: `?note=hello%20world` becomes `?note=hello+world`. Both native ports were deliberately built to avoid this and each has a test asserting an exact untouched query string; `frakContext.test.ts` only reads back decoded values, so it would pass unchanged either way. A link built web-side and one built by either native SDK can byte-differ on identical input, and nothing anywhere would notice.
- **9.2** (§3.2) — Android's tolerant percent-decoder corrupts unescaped non-ASCII where iOS's does not.
- **Stale spec in the TS reference.** `mergeAttribution.ts`'s doc claims hardcoded fallbacks for `utm_medium`, `utm_campaign`, `ref` and `via`; only `utm_source=frak` exists in any of the three implementations, and `resolveAttributionValues`'s docstring describes reading `merchantId`/`clientId` from a context parameter the function does not take. All three platforms agree on the actual, simpler behaviour — the risk is that the next port is written from the comment.

The resolve-response decoder is the second candidate, and it has now produced three real divergences (2.10, block-level forgiveness, and 9.3). There is no TS runtime decoder to conform to: `sdkConfigStore.ts:146` is a bare `as MerchantConfigResponse` cast, so the native forgiveness policy was invented independently on each platform.

Closed in the iOS-only pass on top of round 3 (uncommitted at the time of this update):

- **9.1** — iOS used to report `.dismissed` over a share or copy that actually happened: `SharingPresentation.dispose()` nilled `onOutcome`/`onClose` synchronously, but `share()`/`copy()`/`fallBack(to:)` are independent, deliberately un-cancelled tasks that outlive the sheet, and a swipe landing inside `copy()`'s `await trackSharing()` (no chooser covers a copy, so freely reachable) used to report `.dismissed` over the real `.copied`. Fixed by porting Android's `attributionsInFlight`/`abandonRequested` as `AttributionLedger`, a plain struct in `SharingSheetLogic.swift:113` — outside the `#if canImport(UIKit)` gate, so it is host-tested (`AttributionLedgerTests` in `SharingSheetLogicTests.swift`). `SharingSheetModel` brackets `share()`, `copy()`, `fallBack(to:)` and the `.install` action with `attributions.begin()`/`defer { endAttribution() }` (`SharingSheetModel.swift:82,96,599,609`), and `SharingPresentation.dispose(onSettled:)` asks the ledger via `SharingSheetModel.abandon(onSettled:)` instead of tearing down unconditionally. Three things the port deliberately did not copy from Android, on record: plain `Int`/`Bool`, not `AtomicInteger`/`AtomicBoolean` — `SharingSheetModel` is `@MainActor`, so every read/write of `attributions` is already serialized on one thread, unlike Android's equivalent work which crosses `Dispatchers.Default`/`Main.immediate`; `dispose` releases the model and the pooled web view *immediately*, deferring only the outcome channel — matching what Android's `abandon` actually defers, the `Dismissed` report, never the teardown; and the deferral is bounded by a 5s `SharingPresentation.abandonGrace`. Both of the last two guard against `NativeShare.share()` hanging when a chooser is accepted then torn down (already on record in the smaller-items paragraph in §3.3) — an unbounded deferral that also held the pooled view would mark it lent forever and wedge every later sheet. An ARC hazard found in review, fixed in the same pass: `SharingPresenter.finish` nils its own `presentation` before calling `dispose`, so on the deferred path nothing else retained the presentation — a `[weak self]` completion handed to `model.abandon` found itself already deallocated, silently dropping the merchant's `onResult` and leaving `disposing` stuck `true`, wedging every later sheet. `selfUntilSettled` (`SharingPresentation.swift:28`) now holds a strong self-reference across the deferral window; `settle` (`SharingPresentation.swift:96`) clears it through a local `withExtendedLifetime` so the object cannot deallocate mid-method. A second hazard review found in the same code and did *not* close: see 9.16.
- **9.3** — iOS used to drop *every* placement when one was malformed: `try?` wrapped the whole `[String: ResolvedPlacement]` decode, and Swift's synthesized dictionary decoding fails wholesale on a single bad value. Fixed by `FrakResolvedConfig.decodePlacements(from:)` (`Config/FrakResolvedConfig.swift:113`), which walks a nested keyed container (`PlacementCodingKey`, a stand-in `CodingKey` for the merchant-defined, not-known-ahead-of-time placement ids, `:133`) over `.allKeys` and decodes one entry at a time, dropping only the entry that fails — the Swift shape of Android's `objectMap` per-entry skip. Absent, null, or a non-object `placements` value all still fall through to `[:]`, same as every other field in this initializer. Was the same failure mode as the `translations` regression closed earlier — that fix narrowed one field, it did not change the collection's granularity; this one does.
- **9.6** — iOS had no `contentLost` equivalent for a renderer crash arriving after the page painted; its web view has been `isOpaque = false` all along and the sheet cleared its own background unconditionally, so that crash used to leave a fully transparent, contentless sheet with no system background behind it. Fixed: `@Published private(set) var contentLost` on `SharingSheetModel` (`:36`), set in `onPageUnavailable`'s `pageLoaded` branch (a chooser there would be a share the user never asked for; `contentLost` tells the sheet to cover instead of falling back). `FrakSharingSheet` renamed `ClearSheetBackground` to `SheetBackground(clear:)` and now passes `!model.contentLost`, and layers an opaque `ContentLostSurface` (`Color(.systemBackground)`, matching the loading skeleton's own fill) over the web view in that state.
- **9.10** — iOS could not detect a version mismatch (Android has had `checkSdkVersionMatchesArtifact` since round 3). `scripts/run.sh` gained `check_sdk_version` (`:66`), which greps `FrakSDKVersion.current` and `package.json`'s `version`, dies if either is unextractable (not just on a mismatch — a botched extraction must not read as an empty-equals-empty pass) or if they disagree, runs on `build` and `test`, and is exposed standalone as `bun run --cwd sdk/ios check:version` (`do_version`, `:135`).
- **The `decidePolicyFor` "nearly match" row** (formerly unnumbered, §3.2) — iOS `SharingWebView`'s two `decidePolicyFor` overloads used to "nearly match" `WKNavigationDelegate`: the protocol types the decision handlers `@escaping @MainActor @Sendable`, the code didn't, so they were reached by ObjC selector dispatch alone rather than being static conformance witnesses. Both overloads now declare `decisionHandler: @escaping @MainActor @Sendable (...) -> Void` (`SharingWebView.swift:238,304`), matching the protocol exactly, and the build is warning-free. The row said "verify on the first simulator pass, then match the signature" — the signature is matched ahead of that pass, which (T3) still hasn't happened.
- **B4 / B5 / 1.5** — iOS declared `swift-tools-version: 5.9` while using Swift 6-only syntax, and Swift 6 strict concurrency was forced only by `-swift-version 6` in `scripts/run.sh`, which CI called and a merchant never did — a consumer's own `swift build` or Xcode SwiftPM resolve silently compiled in Swift 5 mode. Fixed: `Package.swift` is now `swift-tools-version: 6.0` with `.swiftLanguageMode(.v6)` on all four targets, and the redundant `-swift-version 6` is gone from `run.sh`. Cost, on record: a hard Xcode 16 floor for anyone resolving the package (`.swiftLanguageMode` is a PackageDescription 6.0 API); `.unsafeFlags` was considered and rejected, since SwiftPM refuses it on any target of a package resolved as someone else's dependency, which this always is. Was in §1 ("Blocking the first publish"); retired here since nothing about it is still landing.
