# Native SDK — open findings

Register of open findings from three audits of `sdk/android`/`sdk/ios` (round 1 over the first tree, round 2 at `51d923ded`, round 3 at `2ae125a71`). Only what is still open or partial is listed; closed findings are one line each in §4. Ids are kept from the original documents (`B*/S*/C*/N*/A*/D*/T*` from round 1, `2.x/3.x/4.x/5.x/8.x` from round 2, `9.x` new in round 3) so commit messages and review notes still resolve.

Rounds 1 and 2 were static. Round 3 ran both suites: iOS 366 tests / 37 suites green, Android 132 tests green (15.4s, >65% of it one test — see T6). Evidence line numbers were re-resolved against the current tree this pass.

## 1. Blocking the first publish

ABI-irreversible or verification-blocking. Everything else can ship late. Two of the four rows below are now decided rather than blocking — they stay in this section, with their state in bold, because the *work* they decided is still landing and the record of why is worth keeping next to what it blocked.

| Id | Finding | Evidence |
|---|---|---|
| A1 / 1.6 | No binary-compatibility gate, no committed `.api` dump. **No longer blocked** — the shape is decided in `09-android-api-surface.md` and BCV is the last of its five steps, since committing a dump ratifies the shape. `libs.versions.toml` has no BCV coordinate at all; `frak-publish.gradle.kts:14` is a comment saying so | `buildSrc/src/main/kotlin/frak-publish.gradle.kts:14` |
| A3 / D7 | **Decided in `09-android-api-surface.md` §1/§3; landing in five reviewed steps.** Step 1 is done: the ten resolved-config classes now have `internal` constructors and no default arguments, so a new backend field is a new getter — no Builder needed for a read model, and the `DefaultConstructorMarker` bridge no longer reaches the dump. `FrakResolvedConfig` gained `displayName`/`displayLogoUrl` so `:frak-sdk-ui` stops walking the tree, and `SharingDependencies` now carries an internal `SharingMerchant` instead. **Still open: the input types** — `SharingRequest`/`SharingProduct`/`ProductDetails` first, then `FrakConfig`/`FrakMetadata`/`AttributionParams`. Original reasoning, still accurate: `FrakConfig` is a 9-parameter constructor with defaults — the synthetic `$default` bridge makes adding a field a `NoSuchMethodError` for an already-shipped merchant binary, and it has already grown once (`preloadSharing` took it from 8 to 9 after the last `.api` dump, which would have broken every merchant had the SDK been published). ### 3.2 Correctness

| Id | Finding | Evidence |
|---|---|---|
| 9.1 | **iOS reports `.dismissed` over a share or copy that actually happened.** `SharingPresentation.dispose()` nils `onOutcome`/`onClose` synchronously to stop a stale, cancelled build from poisoning the next session — but `share()`/`copy()` are independent, deliberately un-cancelled tasks that outlive the sheet. Swipe the sheet away while `copy()` is suspended in `await trackSharing()` (no chooser is up during a copy, so this is freely reachable) and the merchant gets `.dismissed`; the real `.copied` lands on a nilled callback. Android solved exactly this with `attributionsInFlight`/`abandonRequested`, which defers the dismissal until the last attribution reports. iOS has no counterpart | `SharingPresentation.swift:55-70`, `SharingSheetModel.swift:612`, vs `SharingSheetState.kt:283-286,694,703-714` |
| 9.2 | Android `UrlQuery.percentDecode` writes `char.code` into a byte stream, keeping only the low 8 bits of a UTF-16 code unit. Any unescaped non-ASCII character in a value that contains at least one `%` is truncated and then mis-decoded as UTF-8 — `é` becomes a lone `0xE9`, not `0xC3 0xA9`. iOS iterates `Array(value.utf8)` and is byte-safe. The decoder is explicitly tolerant by design, so imperfectly encoded input is the expected input, and this feeds `fCtx` extraction and gap-fill | `net/UrlQuery.kt:96-113` vs `Net/URLQuery.swift:90-107` |
| 9.3 | iOS drops **every** placement when one is malformed: `try?` wraps the whole `[String: ResolvedPlacement]` decode, and Swift's synthesized dictionary decoding fails wholesale on a single bad value. Android's `objectMap` skips per entry. This is the same failure mode as the `translations` regression closed in §4 — that fix narrowed one field, it did not change the collection's granularity. No test on either platform supplies a good entry and a bad entry together | `Config/FrakResolvedConfig.swift:107-108` vs `config/JsonReader.kt` `objectMap` |
| N4 / 5.7 | Partial, closer to closed. Android budget fixed (connect/read 3s/5s inside a 20s deadline). iOS collapsed to one authoritative mechanism (`Deadline.run`, 20s), with `timeoutIntervalForRequest`/`Resource` raised to a 60s backstop that can't fire first. Three mechanisms still exist, but they no longer compete for a budget | `net/HttpClient.kt:284-289`, `Net/HTTPClient.swift:47-73` |
| — | Load deadline isn't cancelled on a manual share/copy. `share()`/`copy()` complete neither `contentSettled` (Android) nor `settleContent()` (iOS), so a 1.5s deadline elapsing after a fast manual tap raises a second OS chooser. Both platforms close the sheet on that path, not just iOS as previously recorded | `SharingSheetState.kt` `share`/`copy`, `SharingSheetModel.swift` `onDeadline` |
| — | `SharingPageAction.Install` has no in-flight guard, unlike `share`/`copy`, which both carry one for exactly this reason (the hosted page's footer stays enabled across the native round trip). Two rapid install taps run two `installPageUrl` fetches and race each other's navigation on the shared web view. Both platforms | `SharingSheetState.kt:528-549`, `SharingSheetModel.swift` `.install` case |
| — | iOS `SharingWebView`'s two `decidePolicyFor` overloads "nearly match" `WKNavigationDelegate` — the SDK now types the decision handlers `@escaping @MainActor @Sendable`, the code does not, so they are not static conformance witnesses and are reached by ObjC selector dispatch alone. Compiles with a warning today and works in every other project that hits it, but the whole outbound channel rides on it. `@preconcurrency import WebKit` does not silence it. Verify on the first simulator pass, then match the signature | `SharingWebView.swift:311,387` |
| — | Android does not reset `SharingWebViewHandle.documentReady` in `onRenderProcessGone`, so an idle pooled view whose renderer was reclaimed still reports a finished document and the next sheet activates by fragment into a dead renderer. **Not a one-line port of the iOS fix**: `documentReady` lives on the handle, `onRenderProcessGone` is on the client, and the client has no reference back. Needs either a callback (mirroring `onLoadFailed`) or moving the flag | `SharingWebView.kt:161,485` |
| 9.6 | iOS has no `contentLost` equivalent. Android added an opaque `Surface` for a renderer crash arriving after the page painted, precisely because a transparent web view turns that into a see-through hole. iOS's web view has been `isOpaque = false` all along and the sheet sets `.presentationBackground(.clear)`, so the same crash leaves a fully transparent, contentless sheet with no system background behind it | `SharingSheetState.kt:203,620-622` + `FrakSharingSheet.kt:147` vs `SharingWebView.swift` `isOpaque`, `FrakSharingSheet.swift` `ClearSheetBackground` |
| 9.14 | Branch-only, narrow, same family as 9.1. On `refactor/android-sharing-sheet-api`, `SharingHost.attach()` clears `pendingResult` *before* posting the buffered-result replay, and the posted lambda no-ops if the Activity it captured is no longer current. Two Activity recreations inside one main-loop turnaround — implausible by hand, reachable via `recreate(); recreate()` in an instrumented test — therefore drop a real outcome permanently. `08` §9.10 lists the replay as untested but not this sub-case. Fix is to clear only once the replay has actually been delivered | `SharingHost.kt:242-247` (branch) |

### 3.3 Public API / DX

| Id | Finding | Evidence |
|---|---|---|
| A2 | Sealed/enum hierarchies make an exhaustive `when`/`switch` a consumer break. Broader than filed: also `Interaction` (Android), `SharingResult` (both). `EstimatedReward` is the only hierarchy with an `Unknown` arm. **Partly decided:** the `Interaction` half is answered by the collapse in `09-android-api-surface.md` §4 (step 3), which removes the hierarchy outright. `FrakError`, `FrakEnvironment`, `RewardTier` and `SharingResult` are untouched and still open | `FrakError`, `FrakEnvironment`, `RewardTier`, `Interaction`, `SharingResult` |
| 9.8 | **Decided in `09-android-api-surface.md` §4: Android collapses to iOS's shape.** `Interaction` took opposite designs per platform. Neither is wrong; nothing documents the asymmetry to merchants | `tracking/Interaction.kt` vs `Tracking/Interaction.swift` |
| 9.9 | `FrakConfig`/`FrakMetadata` are `Hashable` with hand-written `==` on iOS (excluding `logSink`) and reference-identity on Android — two configs built from identical values are never equal in Kotlin. Android already fixed this exact gap for `FrakResolvedConfig` (A10, §4) and didn't carry it to the config types | `core/FrakConfig.kt`, `Core/FrakConfig.swift` |
| 9.7 | `shutdown()` means something materially weaker on iOS. Android cancels one `SupervisorJob` that every background coroutine is structured under. iOS cancels the startup task and the tracker only; its own doc lists what escapes — background config revalidation, `RewardRepository`, the `resetAnonymousId` purge and the eager identity mint, all unstructured `Task`s that can still hit the network after `shutdown()` returns | `DefaultFrakClient.swift:131-147` vs `core/DefaultFrakClient.kt:130-133` |
| A7 | **Decided; specified in `09-android-api-surface.md` §2.** Java is a supported target from day one — supported, not pampered. Kotlin callers get `suspend`; Java callers get a `CompletableFuture` twin per member, named `*Async`. The **sharing-sheet half is implemented** on `refactor/android-sharing-sheet-api`: `FrakSharing.Builder` with no default arguments, a SAM-convertible `fun interface ResultCallback` annotated `@MainThread`, and `warm()`/`present()` deliberately non-`suspend`, so the sheet needs no future twin at all. Config is answered by A3. **Still open: the 15 `public suspend fun`s** across `FrakClient` and the five `*Api` namespaces, which Java cannot call without hand-writing `Continuation` plumbing. Costs nothing to add: `kotlinx-coroutines-jdk8` merged into `-core` in 1.7.0 and the SDK is on 1.11.0 with `api(kotlinx.coroutines.core)` already declared, so `future { }` is on the classpath with no new dependency, minSdk 24 clears `CompletableFuture`'s API floor, and cancellation is free — `future.cancel(true)` cancels the job. **Two things this must do or it regresses on the sheet:** complete on `Dispatchers.Main` (`scope.future(Dispatchers.Main) { ... }`) so a naive `thenAccept` lands on the main thread, and launch on the same `SupervisorJob` that `shutdown()` cancels (cf. 9.7). The `*Async` suffix avoids needing `@JvmSynthetic`, which would otherwise trade Java ergonomics for BCV coverage on the Kotlin surface. `FrakResult<T>` is the right result type and `kotlin.Result` is not — the latter is a value class that erases to `Object` from Java. **Two accepted consequences, both deliberate:** the SDK now carries two async idioms — a `@MainThread` callback for a session outcome, futures for request/response — which is defensible on semantics but is a decision, not drift; and `CompletableFuture` is a heavier mental model for the legacy Java apps that motivated supporting Java at all, callbacks having been the safer shape and declined in favour of a smaller surface. Needs stating once in `05-build-and-release.md` §5 | `FrakClient.kt`, `*Api.kt` |
| D2b | Both harnesses compile against the real SDK and one has run on a device, but neither has exercised the sharing sheet, the install handoff or an inbound deep link | `example/native-{android,ios}` |
| D3 / D4 | Partial. Request logging lands on both platforms (method/host/path/status/duration, never the query string or a header value). Transport-injection points remain `internal` — `HttpClient` is an `internal class` and its `open` hook is a `private val` on it — so a merchant can't substitute a fake transport. `FrakEnvironment.Custom` against a stub server is the only seam, by design per `02-sdk-design.md` §5 | `net/HttpClient.kt:33-41` |
| D5 | Typo in `targetInteraction` fails silently — free `String`, no constants, no validation, on `RewardsApi.best`, `SharingRequest` and `FrakResolvedConfig` | `RewardsApi.kt:29`, `RewardsAPI.swift:27` |
| Q4 | `FrakLogSink` diverges deliberately — a throwing sink is swallowed on Android (`catch (_: Throwable)`), and on iOS the protocol method is non-throwing so a trap inside a merchant's sink brings down the host process, uncatchably. Cheaper to change before publication | `core/FrakLogger.kt`, `Core/FrakLogger.swift` |
| 9.10 | Android cannot publish a version mismatch: `checkSdkVersionMatchesArtifact` is wired into `check` and fails if `FrakSdkVersion.CURRENT` disagrees with `gradle.properties`. iOS has no such gate — `FrakSDKVersion.swift` says it is "kept in sync by hand with package.json," and nothing verifies it. `05-build-and-release.md` §3 forbids retagging, so a mismatch would ship uncorrectable | `frak-publish.gradle.kts`, `FrakSDKVersion.swift` |

Smaller items: `FrakEnvironment.Custom`/`.custom` still default to Frak's internal dev wallet package id/scheme when a merchant doesn't override; `PercentEncoding` was `public` on Android purely to cross a module boundary — **now `@InternalFrakApi`** (`09` §3a), the first and so far only use of that marker; `FrakError.AlreadyPresenting` is unreachable on iOS (the `Binding` makes it structurally impossible) and real on Android; `FrakSdkVersion.kt`'s KDoc points at a `version` in `build.gradle.kts` that doesn't exist. `NativeShare.share()` can still hang if a presentation is accepted then torn down — the refused-presentation half is fixed, and the code says so itself. **Two withdrawn:** `FrakSharingDefaults.HEIGHT_FRACTION` being a `public const val` that inlines into merchant bytecode is fixed on `refactor/android-sharing-sheet-api` — now a `@JvmStatic val` read through a getter, with the reasoning in its KDoc. ### 3.7 The largest un-pinned surface

Not a bug — the highest-leverage structural gap. No golden corpus for URL query editing, gap-fill and attribution merge: **303 lines of code (478 raw), not the ~230 previously recorded**, hand-ported three ways (`queryParams.ts`/`UrlQuery.kt`/`URLQuery.swift`, `mergeAttribution.ts`/`AttributionParams.kt`/`SharingLinkBuilder.swift`), encoding a case-insensitive `fCtx` lookup, tolerant percent-decoding, "never re-encode the merchant's URL", empty-value skipping and a seven-field precedence rule. `golden-sharing-links.json` would close it the way `golden-context.json` closed the codec — note that fixture lives in `sdk/core/src/context/fixtures/`, referenced by path from both native suites, and covers only the binary `fCtx` codec.

Round 3 found three concrete instances of the drift this section predicts:

- **9.11 — the TS reference does not implement "never re-encode the merchant's URL."** `frakContext.ts`'s `update()` round-trips through `URLSearchParams`/`URL.toString()`, which re-serialises the entire query on any mutation: `?note=hello%20world` becomes `?note=hello+world`. Both native ports were deliberately built to avoid this and each has a test asserting an exact untouched query string; `frakContext.test.ts` only reads back decoded values, so it would pass unchanged either way. A link built web-side and one built by either native SDK can byte-differ on identical input, and nothing anywhere would notice.
- **9.2** (§3.2) — Android's tolerant percent-decoder corrupts unescaped non-ASCII where iOS's does not.
- **Stale spec in the TS reference.** `mergeAttribution.ts`'s doc claims hardcoded fallbacks for `utm_medium`, `utm_campaign`, `ref` and `via`; only `utm_source=frak` exists in any of the three implementations, and `resolveAttributionValues`'s docstring describes reading `merchantId`/`clientId` from a context parameter the function does not take. All three platforms agree on the actual, simpler behaviour — the risk is that the next port is written from the comment.

The resolve-response decoder is the second candidate, and it has now produced three real divergences (2.10, block-level forgiveness, and 9.3). There is no TS runtime decoder to conform to: `sdkConfigStore.ts:146` is a bare `as MerchantConfigResponse` cast, so the native forgiveness policy was invented independently on each platform.

### 3.8 The native↔web style contract

Landed in `c821d8fde`/`2ae125a71`; the sheet's chrome is now styled by origin (a document-start CSS-var injection scoped to the wallet origin) rather than by a route-scoped query param. The detailed audit of that change lives in `07-sharing-sheet-audit.md` §1.1a/§1.1b — recorded here only where it leaves something open.

Still open: the `--frak-host-top-radius`/`--frak-host-surface` names are hand-mirrored string literals in Kotlin and TS, each side asserting the other's spelling in its own test, with no compiler link — a rename passes both builds and fails only at runtime. **This is a fourth instance of §3.7**, alongside `queryParams`/`UrlQuery`/`URLQuery` and `mergeAttribution`/`AttributionParams`/`SharingLinkBuilder`, and the smallest of the four: two literals is a far cheaper corpus than `golden-sharing-links.json`, and §3.7 already cites the precedent that worked — `golden-context.json` closed the codec. iOS's correctness additionally depends on those CSS fallbacks continuing to mean "square and opaque", and nothing pins that: iOS injects nothing by design (a second arc inside a SwiftUI `.sheet` reads as a double corner), so it inherits whatever the fallback happens to be. `androidx-webkit` is a new `implementation` dependency of `:frak-sdk-ui` that `02-sdk-design.md` §3's dependency table doesn't list, and `checkDexSizeBudget` has not run against it. Nothing here has been verified on a device.

See 9.13 for why no harness could have caught any of this, and 9.12 for the two dedup items that turned out not to be findings. The argument that 9.13 makes the device tier a precondition rather than a sequencing preference belongs in `05-build-and-release.md` §6, not here — this file stays a register.
